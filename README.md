# Y.Yuya

**AIエージェントを開発の相棒に、一人でプロダクトを作り切るエンジニア**

業務自動化と生成AIの活用を軸に、約4年の開発経験があります。直近ではBPO企業で、月20万件のVoCデータをAzure OpenAIで自動分析する仕組みを作り、約200人月かかっていた作業を1〜2名で回せるところまで圧縮しました。

2023年からChatGPTを開発に取り入れ、いまはClaude Code / Cursor / Codex を役割ごとに使い分けています。定型的な実装はAIに任せて、自分は何を作るかの判断と、出てきたコードの品質を見ることに集中する。この進め方を実務でも個人開発でも続けています。

> ポートフォリオサイト: [yuyayoshiok.github.io/resume](https://yuyayoshiok.github.io/resume/)

自分が困っていることを技術で解決する、というのが出発点です。そのためにフロントエンドからサーバーレス関数、クラウドインフラ、Terraformでの構成管理まで、領域を分けずに一人で作ってきました。作って終わりにせず、毎日使いながら直し続けています。

## 強みの3本柱

### 1. AI駆動開発の実践

AIエージェントを補助ツールではなく開発の中心に置いて、**開発環境そのものを作っています**。

- Claude Code / Cursor / Codex を役割ごとに使い分け
- 依頼内容に応じて処理を振り分ける Claude Code Skill 群の設計と運用
- 定型的な実装はAIに任せ、自分は設計判断とコードの品質担保に集中

### 2. 生成AI・機械学習の業務実装

モデルを動かすだけで終わらせず、**現場で使われ続けるシステムにするところまで**担当します。

- VoC分析: 月20万件の問い合わせを Azure OpenAI で自動分類。約200人月相当の作業を1〜2名の運用体制へ
- 営業確度予測PoC: 数万件規模の商談データを前処理し、LightGBMでモデルを構築。学習用と検証用にデータを分けてAUCなどで精度を確認
- RAG構成: 1万件超のドキュメントから関連文書を検索し、LLMのコンテキストへ渡す仕組みを設計・運用
- 制約の強い環境でも動かす: 外部の実行環境が使えない現場で、VBAからAPIを呼ぶ構成を考えて8〜9台で並列処理

### 3. 現場の課題を聞き、動くものに変える実装力

UIからバックエンド、デプロイまで領域を分けずに担当し、要件のヒアリングから運用が定着するところまで見届けます。

- 非エンジニアの業務担当者に直接ヒアリングし、要件定義から運用定着まで一貫して担当
- フロントエンド: React / TypeScript / Vite
- バックエンド: Python（FastAPI / Flask）・Go・Node.js
- 業務委託先ではWebアプリケーションを一人称で担当し、1〜3か月単位で納品
- チーム開発では Git / GitHub を使い、コードレビューを受けながら実装
- 個人プロダクトをサーバーレス構成で継続運用
  - Google Cloud: Cloud Run / Cloud Functions / Cloud Scheduler / Firestore / GCS / BigQuery
  - Cloudflare: Workers / R2 / D1 / AI Gateway
  - Azure: Azure OpenAI
  - AWS: Lambda / S3 / EventBridge（過去に個人開発で使用）
- Terraform でのインフラ管理、GitHub Actions でのCI/CD、Docker

## 自己PR

**「自分が困るから作る」が原動力**

吃音があり、口頭よりもテキストで力を発揮するタイプです。書いて伝えることを早くから鍛えてきたので、非同期・テキスト中心のコミュニケーションが得意です。

この特性が、データ入力からVBAでの自動化、AI活用へとつながるキャリアの方向性を作りました。正確さと速さで貢献しようとするなかで「この作業、自動化できないかな」と考えるようになり、独学でプログラミングを覚えました。

自分が楽になるために作る、という動機はいまも変わりません。

その延長で、AIアシスタントや音声入力ツールといった個人プロダクトが生まれています。

自分が課題の当事者なので実用性にはこだわりがあり、作ったものを毎日使い続けているのが特徴です。

たとえば自作のAIアシスタントは、その日の出来事をSlack経由で整理してObsidianに残す仕組みとして、すっかり生活の一部になりました。

この感覚は、他の人のために作るときにも役立っています。

業務ツールを作るときは、まず現場の担当者に直接話を聞いて、どこで手が止まっているのかを確かめてから設計に入ります。

非エンジニアが毎日使うものだからこそ、動くだけでなく、迷わず使えて、壊れても直せる形にする。

シフト表の作成を月2時間から10分に、承認プロセスを約50%短縮できたのは、この進め方から生まれた結果です。

**限られた条件の中でやり切る**

資格を取って終わりにせず、Google Cloud・Terraform・Docker・CI/CD は個人プロダクトで実際に動かしてきました。まず動くものを作って現場に持ち込む、というサイクルを繰り返しています。

この進め方は実務でも役立っています。直近では、PythonやGoの並行処理が使えない環境の中で、VBAに排他制御を実装して月20万件のVoCを分析するツールを完成させました。

また、個人開発のインフラを安く運用するためにGoogle CloudからCloudflareへの移行を進めるなど、コストと運用のしやすさを見ながら技術を選べるのも自分の強みだと思っています。

## いま伸ばしている領域

**チームでのレビュー**

これまでは要件定義から運用まで一人称で担当することが多く、コードレビューは受ける側でした。

個人開発だとレビューしてくれる相手がいないので、いまはCodexに設計レビューをさせて、自分の判断を外から検証しています。

規約の確認や実装の粗探しといった機械的なレビューは、CodeRabbitのようなツールに任せられる範囲がどんどん広がっていると感じます。

一方で、なぜその設計を選ぶのか、どう作れば使われ続けるのかという判断は、人が時間を使うべきところだと思っています。

レビューのうち機械に任せられる部分はAIへ寄せて、人の思考はより創造的なところに使う。

そういう前提のチームの中で、設計の判断そのものを磨いていきたいです。

**RAGの精度改善と評価**

いま運用しているRAGは、タグとキーワードで関連文書を集めてLLMに渡す構成です。

実用には足りていますが、ベクトル検索を組み合わせたハイブリッド化と、検索結果が良いかどうかをどう測るかという評価の仕組みづくりが次の課題だと考えています。

作ったものの精度を数字で語れるようになりたいです。
